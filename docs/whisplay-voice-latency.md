# Isolated voice-control latency candidate

Base: deployed chatbot `a17f922`; existing daemon `9d673a6` is unchanged. No deployment, model/context change, dependency, microphone or UI change.

Confirmed original volume-down trace: **one** inference, 1,537 prompt tokens / 31.175 s, 34 generated tokens / 5.298 s, 36.558 s total. No previous conversation turn, memory-summary inference, pre-tool inference or post-tool result generation. The system message was 2,335 characters; the request also included four tool definitions and the device-call instruction. Individual components' token shares were not instrumented and are not guessed. The second user-initiated volume-up request was a separate inference (15.603 s), not a retry. First Piper generation was 3.293 s; observed release-to-audio was approximately 42 s. Production memory is enabled, with auto-save disabled; these settings remain unchanged.

Whole simple commands now bypass model inference, using the same central permission/schema/cancellation dispatcher, existing daemon operations, factual result renderer and speech/memory-before-Home handoff. Supported interpretations are volume/brightness changes, actual system measurements, service availability and Home. Addressing/politeness, direction synonyms, digits/number words and small adjustments are covered. Uncertain, conditional, compound, memory, creative and general conversational text is not fast-interpreted: Qwen remains the fallback, with its model/context/history untouched.

Host precision applies to fallback proposals too: “a little”, “a bit”, “slightly” and unspecified relative adjustments use 10 percentage points. Clear explicit values are preserved. Larger explicit deltas use a live setting read and the existing bounded absolute-setting operation; daemon bounds remain unchanged. Unsupported/out-of-range or unclear numerical requests fail rather than inventing a target. Host validation cannot be bypassed with extra parameters or disabled tools.

History retains the user request, tool call, actual result and factual answer on the fast route. Persistent-memory code, saving, recall, updates, forgetting, persona A and Whisper/Piper are unchanged. There is no second model pass to paraphrase known results. Tests cover fallback, permission denial, precision, failure suppression and history retention; existing speech/memory handoff contracts still apply.

One actual recorded-audio replay measured **2.197 s to playback dispatch**, versus the approximately 42 s physical baseline. Breakdown: real Whisper 1.745 s, host/control 0.072 s, Piper approximately 0.369 s; real playback completed at 5.200 s. Mixer readback verified 80 → 70 → 80%. There were zero inference requests and one ordinary load-only warmup. This was one warmed replay using the existing volume-only test harness while the original app was Home, with its kernel lock held. It was not a fresh PTT test or a deployed latency guarantee. The unchanged original app was relaunched; protected code/config/memory hashes and all service PIDs were unchanged, and capture was closed. An initial coordinator acknowledgement-shape error was corrected before any replay/audio/volume operation; only one replay was performed. Production code was never replaced.

Self-checks: **“Fail-closed proven”** — permission/schema checks, unclear numbers, conditions, wrong targets and disabled tools are covered; **“Behavior executed”** — actual Whisper/mixer/Piper replay and old-fails/new-passes regression; **“Labels honest”** — replay timing, warmup and unverified newly deployed PTT are distinguished. Recommend approval of this isolated candidate, then at most one physical acceptance check. Do not deploy or begin further development automatically.
